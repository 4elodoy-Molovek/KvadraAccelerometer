# Axelo Transmitter (Kvadra Accelerometer)

Распределенная система обработки данных акселерометра на C++, реализующая сбор, фильтрацию и математическую обработку телеметрии в реальном времени. Разработана в рамках тестового задания.

Проект полностью покрывает **Уровень 1** (базовый), **Уровень 2** (gRPC + Protocol Buffers) и **Уровень 3** (mTLS + API Key Auth).

---

## Архитектура системы и взаимодействие компонентов

Система состоит из трех независимых узлов, взаимодействующих через двунаправленные (bidirectional) потоки gRPC:

1. **Узел A (Android / C++ NDK)**
   
   * **Сбор данных:** Напрямую считывает показания аппаратного акселерометра устройства через `ASensorManager` (Android Sensor NDK API) с частотой ~50 Гц.
   * **Передача:** Упаковывает данные в Protobuf-пакет (version, timestamp, x, y, z) и асинхронно отправляет на сервер.
   * **Прием:** Получает обработанные данные (модуль ускорения) от сервера и записывает их в локальный лог-файл приложения (`accel_module.log`).

2. **Сервер (Linux Ubuntu 22.04 / C++)**
   
   * **Маршрутизация:** Выступает в роли надежного брокера сообщений. Использует потокобезопасные очереди (`ThreadSafeQueue`) для передачи данных между потоками клиентов.
   * **Фильтрация:** Отбрасывает подряд идущие дубликаты пакетов от Узла А. Сравнение значений float производится с точностью до 4 знаков после запятой (ε = 0.0001).
   * **Безопасность:** Проверяет mTLS сертификаты и валидирует метаданные (API Key) каждого входящего gRPC-соединения.

3. **Узел B (Android / C++ NDK)**
   
   * **Обработка:** Принимает отфильтрованные данные от сервера.
   * **Вычисления:** Вычисляет модуль вектора ускорения по формуле `sqrt(x² + y² + z²)`.
   * **Возврат:** Упаковывает результат в Protobuf-модуль и отправляет обратно на сервер для передачи Узлу А.

## Инструкции по сборке и запуску

Для упрощения процесса сборки в корне репозитория предусмотрены готовые bash-скрипты.

### 1. Сервер (Linux)

**Требования:** `CMake >= 3.16`, `GCC/Clang`, установленные библиотеки `gRPC` и `Protobuf`.

```bash
# Выдаем права на исполнение
chmod +x build_server.sh

# Запускаем сборку
./build_server.sh

# Запуск демона (порт 50051)
./build/server/server_node 50051 ./certs/ca.crt ./certs/server.key ./certs/server.crt
```

### 2. Клиенты (Android Узел A и Узел B)

Для решения проблем с SELinux (доступ к `/dev/socket` и сенсорам из shell), клиенты реализованы через **Вариант B** (согласно п. 4.6 ТЗ): нативный C++ код собран в виде динамических библиотек `.so` и запускается в фоне через минимальную обертку на Kotlin (Jetpack Compose). Бинарные `.so` файлы исключены из репозитория (`.gitignore`) для обхода ограничений GitHub LFS.

**Требования:** `Android Studio`, `Android NDK r26+`, устройство/эмулятор с API >= 30.

1. Сгенерируйте и поместите клиентские сертификаты (`ca.crt`, `client_a.crt`, `client_a.key`, `client_b.crt`, `client_b.key`) в директорию `android_app/app/src/main/assets/`.

2. Соберите нативные библиотеки через скрипт:
   
   ```bash
   chmod +x build_client_lib.sh
   # Убедитесь, что задана переменная $ANDROID_NDK_HOME
   ./build_client_lib.sh
   ```

3. Откройте проект в Android Studio и запустите сборку APK (**Build -> Make Project**).

4. Установите APK на устройство. В UI приложения выберите IP-адрес сервера и запустите нужный узел (A или B). Лог работы Узла А сохраняется в `/data/data/com.kvadra.accelerometer/files/accel_module.log`.

## Безопасность и генерация сертификатов (Уровень 3)

Взаимодействие узлов защищено с помощью **Mutual TLS (mTLS 1.3)**. Сервер и клиенты взаимно верифицируют сертификаты друг друга. Дополнительно реализована проверка `API_KEY` через gRPC Auth Interceptors.

В корне проекта предусмотрен Bash-скрипт для автоматической генерации самоподписанных сертификатов.

**Пример использования:**

```bash
chmod +x generate_certs.sh
./generate_certs.sh
```

## Обоснование выбора формата сериализации

В проекте используется **Protocol Buffers (proto3)** поверх gRPC (Уровень 2).

**Сравнение с альтернативами:**

1. **JSON:** Удобен для чтения человеком, но обладает высокой избыточностью из-за передачи текстовых ключей и фигурных скобок. Парсинг строковых значений во `float` создает лишний overhead на CPU, что критично при потоковой передаче (50 Гц).
2. **MessagePack / CBOR:** Компактные бинарные форматы. Однако они не предоставляют строгой кодогенерации и типизации "из коробки", что оставляет риск рассинхронизации типов между клиентом и сервером.
3. **Protocol Buffers (Выбранный вариант):**
* Максимально компактная упаковка данных (числа передаются в сыром бинарном виде).
* Автоматическая кодогенерация C++ структур и gRPC-сервисов гарантирует Type Safety.
* **Версионирование:** В `accelerometer.proto` добавлено поле `int32 version = 1`. Это обеспечивает обратную совместимость протокола при будущем расширении системы (например, при добавлении гироскопа), позволяя серверу корректно маршрутизировать пакеты от устаревших клиентов без падения сервиса.
